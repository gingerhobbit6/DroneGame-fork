# Development story

How Site Guard moved from static files to a React, FastAPI and SQLite application, and what was learned on the way. For what is planned next, see the [implementation plan](MASTER_IMPLEMENTATION_PLAN.md).

## Where it started

A browser game in plain JavaScript modules with no build step: about 5,500 lines, including a 1,469-line `main.js` that mixed rules, rendering and UI, and no tests. The simulation design was already strong: seeded random streams, a Kalman tracker, a comms model and real [SAPIENT](SAPIENT.md) messages.

A review found these bugs by running the game:

- `serve.py` handled one connection at a time, so one idle browser socket stopped the page loading.
- A seed in the URL ran as script.
- Reset lost systems the enemy had destroyed.
- Drones drifting under GNSS jamming could hold a wave open forever.
- Results depended on how long you spent building.
- Ghost tracks scored kills from kilometres away.

## Decisions

- **Client-server for data, but the simulation stays in the browser.** See [ADR 0001](adr/0001-simulation-runs-in-the-browser.md).
- **Standard library `sqlite3`, with JSON columns for tuning.** See [ADR 0002](adr/0002-sqlite-with-json-columns.md).
- **SOLID, with a test for each seam.** Add one only if it has two real implementations today, a test needs it, or it separates two reasons to change that already exist.
- **Ponytail for restraint.** No TypeScript, Redux, React Router, react-three-fiber, SQLAlchemy or Docker.

## How it went

**Phases 0 and 1: hygiene and bugs.** Thirteen "modified" files were only line endings. Each fix had a check that failed on the old code first. A rebuild at the first wave made runs independent of build time and placement order.

**Phase 2: Vite.** The npm copy of Three.js was byte-identical to the bundled one, and digests matched in dev and production. Docker holds port 5173 on the development machine, so the game uses 5199.

**Phase 3: separating the simulation.** The risky step, protected by reference digests. They matched in Node on the first attempt, which also settled the worry that Node and Chromium might disagree on floating point. Keeping Three.js `Vector3` in the rules, rather than rewriting it, was what made that possible.

**Phase 4: ghost tracks.** The plan expected radar clutter to be the problem and predicted the fix would make the game much harder. Measuring showed both were wrong: trees caused 80-86% of radar misses inside its range and clutter only 4%, because a 6 m mast sits below the canopy. Raising masts made radar viable, and Mixed went from wave 6 to wave 13. Five lasers now never lose, which is left for a rebalance.

**Phase 5: React.** Every panel became a component while keeping class names, so the game looks the same. Removing HTML built from strings closes the kind of injection found in the review, and a test keeps it that way.

**Phase 6: backend.** Protections were checked against the real server over sockets, as well as in tests. FastAPI masked an oversized-body error as a 400 until the body was read before the app saw it.

**Phase 7: saving.** A laydown saved in one session, reloaded and played with the same inputs gave the same digest. Stopping the server mid-session showed runs being kept safely and saved on its return.

**Phase 8: cut-over.** FastAPI serves the built game on one port, and the strict Content Security Policy held across every tab with no violations. A clean clone was installed and played from the README alone. Two independent reviews then found real bugs that 489 passing tests had missed: importing figures could overwrite `Object.keys`, a run could be reported as kept when it had been lost, closing the page mid-save lost the run, deleting the last row on the last page stranded the Runs tab, and systems and ground leaked GPU memory. Each was reproduced with a failing test before it was fixed, and the GPU fixes were confirmed by counting live WebGL buffers in a browser.

## What kept proving useful

- **Measuring instead of predicting.** Twice the measurement overturned the plan's explanation. Tracks being mislabelled was the first guess in Phase 4, and they turned out to be ghosts.
- **Independent review.** Reviewers given the code, not the conclusions, found what the author's own tests were written not to see.
- **Breaking things on purpose.** Twice a test that looked solid passed with the fix removed. One read its limit from the setting being broken, and another edited a drone that was never engaged in its window.
- **Digests as a safety net.** They caught stale browser files during Phase 1, when a re-run gave exactly the old values.
- **Being honest about test setups.** Digests that looked broken in Phase 5 came from a page on the wrong terrain seed.

## Mistakes worth remembering

- A `git add -A` in Phase 3 committed another author's draft of `docs/REAL_MAPPING_PLAN.md`. Later commits staged only named paths.
- An early test for prototype pollution used an object literal, where `__proto__` sets the prototype instead of adding a key, so it passed on vulnerable code. `JSON.parse` is what real input goes through, and it reproduced the bug.
- A test in Phase 5 looped forever waiting for a spotter that had been shot down, which hung the run for over eight minutes.

## After Phase 8

A whole-repo audit found four bugs that the test suites had missed, each now fixed with a test that failed first:

- The coverage map kept showing the previous laydown, because node ids repeat after a reload and its cache key held little else.
- A connection dropping while the server's answer arrived deleted the browser's kept copy of a run.
- Going back to live from a replay restarted the clock, even with a weapons decision still waiting.
- The message export said it saved every message, but the log keeps only the newest 5,000.

## The wizard

Alex steered this one by editing a wireframe canvas directly: moving the button, marking which decisions they agreed, and striking out in-wave tips because the run should feel like a simulation. The first plan had an AI chat box at its centre. It became a scripted guide, because the browser can only reach its own backend, the game has to work offline, and a coverage gap on a real site should not leave the machine. The chat box stays undecided in `docs/TODO.md`.

Only a real browser showed one bug: the highlight ring landed inside the popup. The popup's blur makes it the frame that fixed-position children are measured from, which jsdom does not model. The ring now draws straight into the page.

## Clicking a system to see what it is

Stage C1 of the planned features: click a sensor or effector on the map, or its button in the Nodes tab, and a panel shows what it is doing, its health, range, ammunition, network link, position and cost. Selection is view state and not a command, so it is never logged and cannot change a run. The reference digests did not move.

Prototyping changed the design before any code was written. Starting wave 1 rebuilds every system with a new id and sometimes a new callsign, so the panel finds its unit again by position. In a real browser, a CSS rule flattened the jammer's list and the panel covered the toolbar with the dock open. jsdom showed neither. The assistant wizard had also taken the planned spot beside the minimap, so the panel moved beside the control panel.

## Small, medium and large

Stages A1 and A2: radar, RF detector, camera and jammer each come in three sizes, chosen from the toolbar or by pressing a hotkey again. Each placed unit now has its own definition over the catalogue's.

The change came in two checks. Adding the sizes and the kind checks left all five reference digests exactly as they were. The renames then changed all five, because names travel in registration messages, but kills, leaks, health and budget matched in every scenario, so the new digests record only the new names.

Checking sources changed two figures. The large radar's assumed 5 km became 4.3 km, scaled from a reported 9 km against a 0.2 m² drone. The large camera became 1.6 km at a fixed 2° view, because range and view have to be set as a pair until the zoom is modelled. Laydown fields and API fields moved to A3, because nothing could write them yet.

The small detector needed testing against the tracker: its ±30° bearing looked likely to fill it with ghost tracks. It does not. Alone, small detectors track almost nothing, and beside a radar they do no harm.

## Editing one system

Stage A3: the Unit panel gains a Configure side for renaming a unit, changing its fields within its size's limits, and selling it. Only fields that already change the game are offered, and arcs, bands and lens choices wait for the stages that give them rules.

A unit's values are worked out when read, from the catalogue and its own settings, so edits in the Sources tab still reach it and no unit can drift out of step. With nothing changed, the saved laydown and the reference digests are exactly as before.

The user reported they still could not click a system. It turned out to be worse: with a placement tool on, clicking a model bought a second one on the ground behind it, because the ground point was far enough away to be legal. My earlier check had pressed Esc first. The running server also had to be restarted, or it would have refused saves using the new sizes and settings, which no test of the code on disk could show.

## Real maps

Started with measurements rather than code. Two test areas showed lidar works and is worth having, that a third of tall cover sits outside OS woodland outlines, and that a whole pack is about a third of the size first estimated. The design held: Three.js stays the only renderer, the rules read the same grids, and generated worlds still give the same digests. A hand test also caught what unit tests had not: the server lists a pack's full fingerprint, and the store compared it with the short form.

The real maps were built on their own branch while the wizard, unit editing and the zone went on `main`, so the two met in one merge. Both were kept. The earlier OpenStreetMap demo stays for generated ground only, as a real world has its own map controls, and the start screen gained the map picker under the wizard's welcome.

## Better placement advice

Alex said the wizard's placement advice did not work well, and measuring agreed. It scored spots mostly on ground height, so on three test terrains interceptors and missiles were pushed about 2.4 km out to the build limit, three systems shared one ridge, and one approach had no sensor cover. It also ignored the zone the player had drawn.

It now tries spots across the build zone and asks the simulation's own detection and line-of-sight checks what each would see or reach in the zone. It judges the two weakest drone types, low flyers first when equally covered, and says why it chose the spot. A camera is valued where another sensor can cue it. On the same terrains, long-reach weapons stay within about 1.5 km and nothing bunches. The honest result is that a medium radar sees only about 9% of the build area against a low FO Strike, which the old advice never showed.

A real browser found one more problem no test could: the suggested ring landed behind the wizard's popup, so the camera now slides it into clear view.

## Map switcher and topography

The map choice then moved out of the crowded control panel into a switcher beside the minimap, with previews drawn from the pack. A topographic map and contours came from the height grid already in every world, so they needed no new data. Marching squares runs over a lightly smoothed copy, as raw lidar makes contours fizz. Two faults turned up on the way: a stale paint could draw over a newer choice of map, and a failed live map could undo a later choice. Location now falls back to a Wi-Fi estimate if high accuracy times out, and a position outside the world offers a map of that place instead of stopping there.

## Real systems in the toolbar

Stage A2 delivered sizes when the user had asked for types: S, M and L are abstractions, and what they wanted was to choose a real radar and set it up before placing it. Clicking a toolbar row now opens a list of the real systems of that kind, with the settings the next one will be placed with. New catalogue entries left the reference digests alone, because each system's name is only carried once it is placed.

The lesson is about reading the request. It had been said more than once, and each time it was answered with a plan stage instead.

Alex then asked for Leaflet-style light and dark maps, and reported that location timed out on a weak connection. Leaflet itself draws flat tiles in the page and cannot wrap a map over 3D ground, so it was not used. The light and dark maps are the pack's OS map recoloured, which works offline and needs no new provider. Live tiles now appear as they arrive. Location asks for a rough and a precise reading together, and uses whichever comes first.

Alex confirmed the project is non-commercial, which allowed EOxCloudless for satellite and hybrid styles across Britain on the start map. It needs no key. It is 10 m per pixel, the same as the packs, so it adds coverage rather than sharpness.

Alex then found that a sensor could not stand in a gap between houses. Placement read the 20 m grid, where any cell with enough building in it counts as solid, so about 57% of marked spots on both real maps were not on a building at all. Placement on real maps now reads the true outlines. Line of sight still reads the grid, as changing it would change how every real-map run plays.

## Magazines

Alex asked for magazine depth, with each system showing its count, rounds fired, storage, reload time, cost per missile and range when clicked. Asked what the $15M should become, they chose to keep paying per shot as well, so a launcher can now run out of money or rounds. That made the change smaller than the plan: prices and saved runs stay as they were. Storage and reload had been left out of the plan, and they became the core of it.

A radar has no rounds, so sensors show scans, detections and scan period in the same rows, and jammers show time spent jamming. The reference digests were re-baselined, because reloading changes runs: a Mixed laydown now leaks a drone it used to stop.

The balance tool shows the rule matters and is not yet balanced. The Mixed laydown now falls at wave 7, not 12 or 13, with about $9.6M unspent, because nothing refills storage. One of everything with 3 lasers went the other way, from about wave 12 to about wave 25, because missiles that run out stop draining the budget.

Resupply followed, which raised a question the plan had not faced: if firing costs money and rounds cost money, a bought round would be charged twice. Bought rounds are now marked as paid. Alex also pointed out that the range rings had gone. They had not: "Show ranges" was on and the rings were being drawn, but at 35% opacity and a pixel wide they vanished against the bright OS map, which arrived after they were tuned on dark ground. Real maps now draw them wider, stronger and darker. Alex's own comparison with the original game is what exposed this, because no test looks at contrast. The "New laydown" button did what they wanted but its name hid it, so it became "Clear map".

The first tests passed for the wrong reason. Starting wave 1 rebuilds every system, so they were changing units that no longer existed; a failing hand-over test exposed it, and they now act after the rebuild.

## A tidier SAPIENT panel

Alex called the SAPIENT panel a hot mess: ten tabs in one list wrapped over two rows, and it opened on the raw message log. The tabs now sit on one row under five small headings (Live, Comms, Plan and cost, Records, Reference), so all of them stay one click away and nothing has to be expanded first. A two-level menu was the other option, but it would have hidden tab names behind a guess. The panel now opens on Nodes, which says what each system is doing. Tab ids did not change, so the wizard and tests still reach them.

The map buttons and map credit drew over the panel, and at 800x600 it ran 14 px off the left of the window. Both are fixed. Inside the tabs, the empty JSON box no longer takes half the Messages tab, the filter chips fit on one row, and the Network diagram closes up its rows so a system can no longer fall below the canvas where it could not be clicked.

## More sizes and acoustic sensors

Alex asked for other sizes of laser, missile and interceptor, and for acoustic sensors in three sizes, using real kit with public figures. Each new entry names a real system, and its `ref` separates what is published from what is assumed. The sourcing paid for checking: the article first cited for one acoustic station's range and price turned out to hold neither, so it was replaced by the one that did.

Real prices do not always rise with size. A long-range acoustic station is reported at about $500, cheaper than a medium array, and the LOCUST laser at about $8 million, four times the $2 million figure for the larger DragonFire. The figures were kept rather than bent to fit, and the test that demanded rising prices now covers only the older kinds. Launcher prices and most magazine figures remain placeholders, and each one says so.

Acoustic sensors added a real rule, not just a row: they need no line of sight and hear drones that make no radio signal, but hills and built-up ground cut their reach. Those loss factors and each drone's loudness are assumptions.

Models now scale with size and are 40% smaller overall. The scale also sets where a shot leaves the launcher, so the reference digests were re-recorded. The eighth toolbar row pushed Sell out of sight on a normal screen, which only a browser check showed, so Sell is now pinned to the bottom of the toolbar.

## Threats by name, and real ones

The wizard recommended whichever system was the medium size, whatever it faced. It now reasons from the threat: the faster a drone flies, the further out it must be seen, so it picks the cheapest system of a kind that gives a minute's warning of the most threats (twenty seconds for a weapon). The player can plan against every type or one drone. A small fixed-wing spotter gets a small radar, and a low fibre-optic drone calls for the large one, because clutter caps a radar's reach against low flyers.

Abbreviations such as FO and FW went from the screen, including the tags over drones. The alert text carries the names, so three reference digests were re-recorded, and every other figure in them stayed the same.

Real drones are data on top of the four types, not new rules: each one starts from its type and overrides what is public. So interceptors, the wizard and the debrief treat a Geran-2 as a fixed-wing strike drone, and the waves are untouched. Research found less than hoped in places. No named Chinese military fibre-optic drone has published figures, so the entry is a commercial one and says so, and no source gives a munition mass for most commercial drones, so those are labelled assumptions.

## Real ranges, UK systems and range from where you stand

Every sensor and effector was checked against datasheets where they could be read. The IRIS sheet gives real test figures by drone weight, so its 2 km became 3.1 km. The A400 sheet gives a range for each radar cross-section, and its table follows exactly the fourth-root law the game already used, which is a useful independent check. Eight UK systems were added, in their own file so that the catalogue stays under the line limit.

The first pass at RF ranges was wrong. The AARTOS was cut to 5.6 km by taking the same fraction that Dedrone publishes between its ideal and normal figures. The user questioned it, and a link budget showed 14 km was believable: the "normal" figures already include real-world losses, and the game applies those itself from terrain and trees, so discounting them counted them twice. That led to the bigger change. A catalogue range now means an open field, and one path model (ITU-R P.526 Bullington, Weissberger for trees, the earth's curve) gives what a spot really gets. Detection, jamming, the rings and the path profile all call the same code, so the prediction cannot disagree with play. Sionna and other ray tracers were considered and left out: see ADR 0003.

The old rule that hid RF behind a hill entirely, and only slightly weakened it in forest, was backwards. Measured foliage loss is far higher than the old figure, and signals do bend over hills. Reference runs moved by a few kills, and how long each laydown survives barely changed.

An audit of the tracker, measured rather than read: one or two RF detectors alone never confirm a track, which is a deliberate rule because two bearings always cross somewhere. Three do, with about 160 m mean error at a 3 degree bearing error, and 2.9 km at 30 degrees. A fourth adds little.

## Drawing the area to defend without the wizard

Alex pointed out there was no way to draw the area to defend on the map outside the wizard. The tool already existed, but only the wizard's zone step could switch it on. A new button beside the minimap now opens a small panel to draw, undo, close and clear the area, and shows how much of it the sensors can see for each drone type, using the wizard's own scoring. It is still a planning aid that stays out of the simulation, so drones attack the same way whatever is drawn.

## Drones attack the drawn area

The drawn area had been a planning aid, and Alex asked for drones to attack it instead. A closed outline now goes into the simulation as a logged command and saves in the laydown. Each strike drone aims for a random spot inside it, spotters circle its centre, and the fusion node measures threats from that centre, so it engages whatever is closest to the area. FPV and FO strikes can still turn on a loud emitter.

It locks when the first wave starts, like the laydown. Runs with no area draw no extra random numbers, so the recorded reference digests did not change. Systems can still only be built within 2.5 km of the station, so a far area is deliberately hard to defend.

## Defending anywhere on the map

Alex tried to draw a site and was told it was too far from the station. The first version of the attacked area kept the station as the middle of everything, limiting drawing to 5 km because drones appeared on a ring around it. Alex's point was that the player should be able to defend anywhere in the map region, not a set site. So a drawn area now replaces the station: drones start out from the area's centre, and you can build anywhere on the map. Near the map's edge an attack starts at the edge, and with under 2 km of room it comes from the other side or from the middle of the map, which is a game rule. With no area drawn, every number is the same as before, so the reference digests did not change.

Once people and the patrol prototype were merged, they still kept the station's 2.5 km limit, each with its own copy of the check. Placing systems, placing people and walking a route now share one rule in `attack-area.js`: with a drawn area or a patrol, anywhere on the map, otherwise the old ring. An area and a patrol each refuse the other, since only one of them can be what the enemy attacks.

## Rounds that can miss, and error that grows with range

Until now a guided round always arrived, and a laser did the same damage at any range. Each weapon now has a hit chance, lowered by evasion, by how fast the target is against the round, by range and by the quality of the track when it was fired. That last one is what ties sensor accuracy to results for the first time. Where there is evidence the figure is worked back from it: with the other effects, the Sting's claimed 80 to 90% comes to about 66% against an FPV, close to the 68% average President Zelenskyy gave, and the P1-SUN's $3,000 a kill at $1,000 a drone comes to about 1 in 3. Most others have no published rate, and say so.

A beam stays at full strength to a quarter of its range and then falls with distance, so dwell doubles when range doubles, as ST Engineering publishes for its CDLE laser. Sensor error follows the monopulse relationship, where error goes with 1 / sqrt(SNR), so it stays near the quoted figure close in and is about 2.2 times larger at the limit of reach. Hills and trees shorten the reach and so worsen it too.

Measuring the first version showed a problem the code did not show. The Mixed laydown fell from wave 11 to wave 7, and leaks were all fixed-wing drones. Its one missile launcher was firing, then sitting idle for a 40 s flight while others got through. It was a fire control flaw that perfect rounds had hidden. Launchers now shoot, look and shoot while there is time, salvo when there is not, and move to the next target while their rounds fly. Mixed then reached wave 9 or 10, spending far more of its budget.

## Any mix of drones in the waves

Another session had already added 21 real drones, but only to the sandbox and the planning tools. This one added three it had left out, the Geran-3 jet, the ASN-301 anti-radar drone and the Wing Loong II, and let the waves send any ticked mix. Each wave keeps its size and timing, and each type's place is taken in turn by the ticked drones of that type, so the default mix builds exactly the waves it did before and the reference digests did not move.

Measuring each country's drones against the Mixed laydown showed how much a game rule now matters. Generic waves last to wave 9 or 10, Russia's to 6 to 8, China's to 2 to 4 and Iran's to wave 2. Iran's drones are all fixed-wing, and interceptor drones are barred from fixed-wing targets, so one missile launcher faces them alone. That rule was always unrealistic, since a Sting is built to hit Shaheds, and it is now the main question for balance.

Alex chose to lift it for the Sting and the P1-SUN, leaving the small net carrier limited to small, slow drones. Hit chance already falls as the target gets faster, so a Shahed is a fair shot and a jet a hard one. Against Mixed, Iran's waves then lasted to wave 11 or 12 instead of 2, China's to 4 or 5 and Russia's to 8 or 9. The generic game got easier too: Mixed held to wave 15 to 17 instead of 9 or 10, and eight interceptors with three compact radars to 14 to 16 instead of 4. Generic waves may want strengthening to match.

## Choosing a site

Alex found choosing a site clunky, and could not tell how to do it. The start buttons were below the fold, the map opened zoomed into one pack with no sign of the others, the ways to choose were scattered around the card, and **Guide me through it** stayed disabled until a site was already chosen, so the guide could not help with the choice.

The start card now lays out three numbered ways beside a bigger map, with the buttons always in reach, and all of it works without the guide. **Guide me through it** now starts on the card, and says what to do next from what has been chosen. The map highlights map packs, the lidar inside them, and the 100 km squares of OS data already downloaded. Choosing somewhere with no map lists what a build would use and what it would download. That comparison happens in the browser against a list of squares from the backend, so looking at a spot sends nothing anywhere. The map only zooms for a choice the player made.

Alex then asked how to switch map tiles, because hiding Leaflet's layer list behind its icon had made it hard to find, and suggested a world map with obvious overlays for loaded data. So the map now opens on the world, with a dot of a fixed size for each pack, which can be clicked from any zoom. Buttons above the map choose the style, and tick boxes below it control the loaded data and double as its legend.

Alex also asked to select anywhere in the world. The map can move there, but real maps are not global: packs need OS open data, and real-world coordinates are on the national grid. So a spot outside Great Britain is refused plainly, and global maps are recorded as a project of their own.

## Estonia

Alex asked whether Estonia had topographic maps, around Narva or Tapa. It does, and they are free to use, so Estonia became the first real maps outside Great Britain, starting with Tapa, because Estonian data stops at the Russian border and leaves half of Narva empty.

The saving grace was that northings on the two grids never overlap, so a position says which grid it is on, and nothing that carries an easting and northing needed to change. The builder gained a second set of sources. Whole-country files were chosen over asking for one area at a time, because downloading them gives nothing away about the site, even though it costs about 7 GB once.

## Simulated people

Alex asked for fake people on the map, in groups, very small and realistic, with a protection level, so that attacks could cause casualties. The first design rule was that people must not disturb the attack. Each blast therefore rolls from a stream seeded by the drone's id, and nothing is read from the run's own stream, so a run with people gives the same kills, health and budget as one without. Casualties join the digest only when a laydown has people, so every older digest still holds.

Two things in the existing game shaped the rest. A drone counts as hitting the site at the 150 m edge of its disc, so blasts measured from there could never reach staff in the middle. A site strike now lands inside the disc for this purpose, aimed at the middle with scatter. And the camera stopped 400 m from the ground, where a person is about four pixels tall, so true scale would have meant never seeing anyone. The camera can now come to 40 m, and each group has a Look button.

A real browser found what the tests could not: the green placement marker was large enough to hide a whole group up close, and a fourth figure squeezed the HUD's stats row together.

The casualty figures are round-number assumptions and are labelled so in the Sources tab. They are not weapons-effects data, and they should not be read as any.

After main gained drawn attack areas, a strike aimed at a spot inside the area now blasts there rather than scattered over the station. People also joined the wizard as an optional step before the rehearsal, so a rehearsal can show casualties. A test measures every figure drawn at between 1.55 and 1.95 m tall and about half a metre wide on both kinds of ground, because generated ground draws trees and houses twice life size and people must not pick that up.

## A patrol prototype

Alex wanted to explore protecting a moving patrol rather than a fixed site. The design is in `docs/PATROL_MODE.md`, and a first slice is playable: a group of simulated people walks a looped route with a Blighter A800 ahead and a Rapid Ranger behind, strike drones home on them, and the patrol halts while the launcher engages. Speeds and spacing are labelled assumptions in the Sources tab. People now take the H key, as 8 belongs to the acoustic row.

The fixed-site digests did not move, because a run with no patrol runs none of its code. The patrol draws no random numbers, so it walks the same way every run.

A browser run found what the tests had missed: nine strikes on the patrol and no casualties. A strike counts once it is within 30 m, and the blast went off where the drone was, beyond an FPV's 25 m casualty radius. It now lands on the patrol, as a strike on a system lands on the system.

## Radar arcs

Stage A4 started with where a radar looks. A fixed-panel radar now covers only its arc: 120° for the EchoGuard and the Spexer, and the published 90° for the Blighter A800 and A400. More panels sit side by side, each at the price of another head, and three or four cover all round. Rotating radars still see all round. Every radar also covers a band of elevation from 10° below the horizon, so a spotter close overhead can pass above the beam, which the published 80° of the EchoGuard and the assumed 60° of the IRIS make plain.

A radar faces away from what is defended unless it is turned, worked out when read rather than stored. So it follows a drawn area, and a patrol's escort radar faces outward from the patrol as it walks. Turning it is a free setting; reset, it faces away again. The rule lives in `sim/sensor-model.js`, and detection, false alarms, the range prediction and every view that draws range go through it, so the rings show a wedge and cannot disagree with play.

This was a deliberate balance change, so the reference digests were re-recorded. The laser laydown, which watches with three Small radars, now lets one drone through where it let none, and the jammer laydown kills 18 instead of 21. The mixed laydowns end the same, with only their messages changed. `GAME_VERSION` moved to 0.6.0.

A4's last piece came later: an arc per panel on the fixed-panel radars. A panel steers its beam, so told to search a narrower arc it spends the same scan on less sky and reaches further, by the fourth root of the arc given up, as a lower top edge already did for elevation. A quarter of the arc, down to the 30° floor, reaches about 40% further, and sees nothing at the old edges. A rotating radar turns all round whatever it is told, so it has no such setting. The standard is the catalogue's arc, so the digests did not change.

## Tracker timing

The tracker's clocks were set for sensors that report about once a second: a tentative track went after 2.5 s without an update, a confirmed one went to coasting after 1.6 s and was dropped after 5 s. A radar scanning every 2.5 s or slower could never confirm a track, so the scan period stopped at 1.5 s. Now every measurement carries its sensor's update interval, and a sensor slower than once a second stretches those clocks by that interval. A track only coasts or drops when every sensor that fed it has missed as many of its own updates, so a slow radar keeps a track a fast camera has lost. Waiting bearings, the sources named in fused reports and kill confirmation follow the same rule. Sensors faster than once a second keep the old clocks, so the reference digests did not move, and the scan period now goes to 5 s. A slower scan still reaches further, by the fourth root of its period, so a 5 s scan reaches about 1.5 times as far with data five times older. Whether that is a fair trade is for the balance pass.

## The rest of the radar

A4 finished with what a radar's hardware and settings do. A Medium or Large radar can be built 2D, 30% cheaper, and then measures no height. Its tracks are flat: placed at a guessed height, with their error and distances measured across the ground, so an effector still finds the drone. A camera cued to one looks at the guess first, then steps up through the sky a view at a time. Tracks that two radio detectors make by crossing bearings never had a height either, and are now treated the same way. A radar can be built for another band. Higher measures angles better, because angle error goes with wavelength, and sees small drones a little further, at a higher price; lower is cheaper and worse until A5 brings rain. The beam's low edge can be raised, halving ground clutter false alarms for every 10°, but low flyers close in pass under it. Its top edge can be lowered, which searches less sky and so reaches further by the fourth root, but leaves a gap overhead. Up to three blanking arcs see nothing, so they raise no false alarms there either. The clutter filter trades how close a low flyer must come against false alarms, and a high filter misses drones moving slowly towards or away from the radar. Micro-Doppler names a multirotor or a fixed wing inside half a radar's reach. Robin Radar and Blighter both describe it for the IRIS and the A400, so it is standard on those two and a paid option on the rest.

The first camera search swept up and down without stopping. It is rarely at the right height when it takes its look, and with micro-Doppler off it cost the mixed laydown its site on seed 1. Holding three looks at each height put that right. Over six seeds the ways of searching were within noise of each other, so the choice rests on the design: look at the guess first, as before, then search.

The reference digests were re-recorded. Micro-Doppler classifications change the messages of every laydown with an IRIS. On seed 1 the mixed laydown kills one more drone and spends $600k less; on seed 7 it ends the same and spends $400k more. `GAME_VERSION` moved to 0.7.0. The beam's low edge is a negative number and blanking arcs are a list, so the API's settings schema now allows both, still checked for shape.

## Conditions and cameras

Stage A5 added the light and weather a run is fought in: a clear day, dusk, night, or rain and haze. It is chosen on the start card or in the control panel until the first wave, saved with the laydown so a run replays, reported by every sensor over SAPIENT, and changes how the scene is lit. It works through one place, a unit's own range, so detection, the rings, tasking and a laser's reach all follow it. A camera keeps the range of its better channel: visible light fades at dusk and is almost blind at night, while thermal works on, and rain and haze cut both. A faster lens gathers more light and keeps more of it. In rain, a K-band radar keeps 75% of its range and an S-band one all of it, and a laser beam half. Radio is not affected. A clear day changes nothing.

Cameras now follow their optics. A drone covers 4 pixels at the edge of a camera's reach, where it is detected; the airframe is named at 8 pixels and named surely at 13, so a camera sees some drones it cannot yet name. A zoom camera searches at its wide view and zooms to its track view on a cue, which reaches four times as far on the medium camera and fourteen times on the large one, then widens again when half its dwell has found nothing there. The large camera used to sit at one fixed 2° view; now it searches at its lens's wide 7.1° end, about 450 m, and reaches about 6.4 km on a good cue. Channels, resolution, the lens's F-number, a laser rangefinder and the slew rate are paid hardware; the track view, search arc and sweep rate are free settings, each with its own cost in play.

Over six seeds of the mixed laydown, a clear day ended much as before, 411 kills and 2 leaks against 413 and 6, and rain was harder, 397 kills and 6 leaks. Dusk and night played the same as a clear day there, because its cameras have a thermal channel; only a visible camera is blind at night, which is the saving it buys. The reference digests were re-recorded, because every sensor status now carries the conditions and cameras name only what covers 8 pixels. `GAME_VERSION` moved to 0.8.0.

A5's three leftovers came later. Rain is noise to an acoustic sensor, so it keeps half its reach, as it does in a built-up area. Thermal light is long enough to blur: a lens spreads a point over about its wavelength times its F-number, so the large mid-wave camera at f/5.5 already spreads light over 22 µm on 15 µm pixels, and finer pixels buy it nothing, while a faster lens sharpens it. That makes a faster lens worth far more on thermal than its price assumes, a question for the price review. And a camera that identifies a drone now names its model, as the track's label, the authority prompt and the kill alert show. Cameras used to leave a track once they had named its airframe, so they almost never came close enough to identify one. A first try sent them back to every classified track until they named its model, and over 36 seeds the mixed laydown lost 6 runs against 2: a camera busy with a far track could not answer a new one. So a camera now comes back only to a track near enough for its model to be named, and a new unclassified track cuts that look short. Over the same 36 seeds the mixed laydown then killed 2,336 drones with 21 leaks and an average health of 79, against 2,337, 32 and 68, with 2 runs lost each. The reference digests were re-recorded and `GAME_VERSION` moved to 0.11.0.

## Radio detection

Stage A6 began with what a radio detector hears. A drone used to roll a radio band at random, 2.4 or 5.8 GHz, whatever its links were, and a detector heard it on any band. Now a drone radiates on the bands of its own control and video links, and a detector hears it only on a band it covers: the small detector, which listens at 2.4 and 5.8 GHz, no longer hears an Orlan-10 on 900 MHz, while the medium one hears a spotter on 900 MHz, which carries further than its video. The path is worked out on the lowest band it hears, and the report carries that band's frequency. A jammer likewise works out each link it jams on that link's own band, which removes an old shortcut. The wave still draws the old band roll, so every wave flies as before.

Your own jammer now deafens your detectors: while it jams, a detector within its range cannot hear the bands it fills, as it already cuts your own links. A detector carries a classifier library. Every catalogue detector comes with the commercial one, which knows DJI and Autel links and so names those quadcopters; a hobby library names the FPV, a tactical one the spotter, and with none it hears energy and nothing more, with twice the false alarms. A library that does not know a link still reports a drone, as before. Receiver sensitivity doubles its reach for every 6 dB, and direction finding by angle of arrival gives a bearing good enough to cross with another, where a sector gives only a rough one. All three are paid hardware.

The mixed laydown over twelve seeds ended at 781 kills and 11 leaks, against 814 and 5 before. That looked like a loss until the same comparison was run on the old code with one extra dice roll per scan, which changes no rule: it ended at 793 kills and 12 leaks. Every leak was a fixed-wing strike drone, which emits nothing, so these runs mostly measure chance, and the six-seed comparison in A5 can say no more than this. The reference digests were re-recorded, and only the mixed laydowns changed. `GAME_VERSION` moved to 0.9.0.

## Jammer reach

The second part of A6 settled how far a jammer reaches. The bands it is fitted for are now paid modules. Every catalogue jammer comes with all four, because the game always let any jammer jam any band, and leaving one out saves money; a band that is not fitted can never be switched on. A jammer can have an omni antenna or a sector one: 10 dB over 60°, so it reaches about three times as far, but only through that arc, which faces away from what is defended unless turned. The arc governs everything a jammer does: which drones it jams, when the fusion node switches it on, which of your detectors it deafens, which of your links it cuts, and the ring drawn for it.

A control link is now easier to jam the further the drone is from its operator, because the jammer only has to be louder at the drone than the operator is. The launch point stands in for the operator, and a jammer's quoted range is taken as against a drone 4.5 km from its operator, about where one on a 6 km run comes within reach of a jammer near the site. A first try at 5 km cut the mixed laydown's jammer kills by a fifth, so the reference moved to where the quoted range holds. Video is still jammed at the drone, a marked shortcut, as its receiver is really with the operator. Each band jammed also makes a jammer louder to emitter-seeking drones.

Over twelve seeds the jammer laydown killed 223 drones against 217, and the mixed laydown 768 with 11 leaks against 781 and 11, which is within chance. The mixed laydown's jammers, 800 m out, killed 120 drones against 142: a drone meets them while still nearer its operator, which is the rule doing what it should, and a reason to keep jammers close in. The reference digests were re-recorded and `GAME_VERSION` moved to 0.10.0.

## A jammer's own ears

The last part of A6 gave a jammer a receiver of its own. It is paid hardware, priced as a Small RF detector with the same classifier library, and it hears a drone on the link bands the jammer is fitted for, as far as the jammer reaches. It cannot hear through noise on those bands: its own barrage fills them, and so do your other jammers nearby, by the same rule that deafens your detectors. That rule now lives in `sim/jamming.js` with the rest of a jammer's reach, shared by drones, detectors and the fusion node.

The receiver opens two choices. Reactive jamming follows only the links its receiver hears and its library knows, and breaks them twice as fast at half the noise, but it leaves GNSS and every other drone alone. And a jammer can now be switched on by its own receiver instead of the fusion node, which keeps it working when its link to the network is down, though it cannot hear a drone that sends nothing. A barrage switched that way is deaf to the bands it fills, so after hearing nothing for a while it stops to listen: 1 s in every 4. A jammer can also be switched by hand, from the Unit panel, and a saved laydown keeps the switch. Every new setting's standard is the old behaviour, so the reference digests did not change.

The last of A6 went to radio detectors: the bands they monitor and how much they take in at once. A detector can drop bands its hardware covers, hearing nothing there but cutting the false alarms each band brings. A narrow receiver costs a quarter less and takes in one band at a time, so it reports once per band it monitors: a Medium detector on all three bands comes round every 3 s, and on one band every second, as now. A real receiver steps through bands far faster than that, so the game stretches it to make the choice felt. A sensitivity for the jammer's receiver was dropped from the list, as hearing further than a jammer can reach would change nothing.

## The balance pass

Stage A7 started from the to-do note that five lasers never lose. Measured over six seeds, that was no longer true: since the Small radar dropped to a 120° arc, the five-laser laydown fell between waves 9 and 22, to drones that came in through gaps in its cover. A sweep of the new unit settings, one at a time on the mixed laydown, found no free win. A 5 s radar scan reaches half as far again, but the laydown lost at wave 9 against 15. P1-SUNs in place of Stings lost at 9.5, because they miss more and run out of rounds. The faster camera lens, dusk, night and rain stayed within the usual spread.

The lasers told a different story. With three panels on each Small radar, all-round cover for $180k more, five lasers reached wave 30 on every seed without a leak in the first ten waves, and so did two lasers costing $5.2M in all. Half the beam power did as well as full, so a laser's burn was never what limited it. In the game a laser burned a small drone in about a second and switched targets at once. Raytheon's 15 kW laser reportedly took 34 s to down three drones, with about 5 s of dwell on each, so about 6 s a drone went on finding and laying on the next. A laser now takes 4 s to swing onto each new drone, or onto one it lost from view, before its beam goes on. The RF weapon steers its beam electronically, so it has none.

With full cover, five lasers now fall between waves 26 and 32, and two at about 20. Beam power matters again: two lasers last about 15 waves at half power and 23 at one and a half times. The reference digests were re-recorded, as the laser laydown kills 121 drones in eight waves against 124, with the same leak, and `GAME_VERSION` is 0.12.0. The balance tool now plays the all-round laydown too, since the standard laydowns hid the problem. Lasers stay the best buy for their price, but the DragonFire's $2M is a placeholder below the smaller LOCUST's $8M, which is for the price review.

B2, the balance of racks, storage and reloads, came next and changed nothing. Halving, doubling or lifting each limit moved no laydown except the mixed one, where only the Sting's magazine mattered: 6 rounds gave 14 waves, 12 gave 15 and 24 gave 18. That is a limit worth refilling for, not a wall, so the assumed figures stay. The runs showed what does end a game instead. A laydown loses when its one radar is destroyed, because fixed-wing drones are radio-silent and nothing else sees them far out: the mixed laydown lost its radar in wave 14 and fell in wave 15, and the eight interceptors went blind when their compact radars were hit, at about wave 5. The Coyote earned little for its $1M: it fired 9 rounds in 15 waves and killed no fixed-wing drone, because Stings take those tracks first, and a second radar in its place lasted 18.5 waves against 15.2. Both are left in the to-do list, as they are questions of price and design rather than rack size.

The systems added outside the plan were measured the same way, on the mixed laydown, and none was too strong. Six $50k Medium acoustic sensors helped, 16.5 waves against 15.2, and the NASAMS in place of the Coyote cost $4M more for 15.5. The $500 Large acoustic stations were the surprise: added to the laydown they made it worse, 11.2 waves with twelve of them, and spent about $4M more. They confirm fixed-wing tracks early and far out, and the Coyote, kept for fixed-wing tracks, then fires as soon as one is named: 29 rounds in ten waves against 1, for the same kills. Their many 10° bearings also handed a fixed-wing classification to quadcopter tracks now and then, and 5 of those 29 rounds went at quadcopters.

That looked like the Coyote wasting its rounds, and Alex chose to hold it until a fixed-wing track came within 2.5 km. Measured, the hold did more harm than good: the mixed laydown lost a seed at wave 9 when four fixed-wing drones reached 2.5 km together, and the stations still burned money. No Sting had been on any of the Coyote's tracks, so its rounds were not wasted. The real cause was ghost tracks. Twelve stations' false alarms, each a 10° bearing, crossed and confirmed tracks where there was no drone, 4.5 of them at any moment against 0.6 without the stations. Ghosts near the site came first, so each Sting was sent to one, found nothing and was held off it for 3 s, then sent to the next, and had a task only 5% of the time. Alex asked for something realistic that works. A real fire-control system does not keep sending weapons where one has just looked and seen nothing, so the hold was reverted and a finding of nothing now holds that track back from every effector for 10 s. With the stations, the Stings now have a task 31% of the time and the mixed laydown lasts 16.0 waves, not 11.2. Over twelve seeds it changed little elsewhere, and one of everything went from about 18 waves to 21. Holding only tracks whose position was good was tried as well and did no better.

Alex then asked for the published success rates to be replicated. Few published figures are hit rates per shot; most are shares of a raid or bare kill counts. Three were usable. Ukrainian crews and Wild Hornets report two or three interceptors a Shahed, and the Sting already takes about three in play, so only its note changed: the 68% Zelenskyy gave is per target, which the note had read as per round. The Norwegian Air Force gave NASAMS 94% over about 900 targets in Ukraine, and in play it was 80%. Even at a hit chance of 1.0 it reached only 83%, because every round lost up to a fifth of its chance to evasion, whatever its speed. A missile eight times faster than a drone barely notices it turn, so evasion now costs a round less the faster it is than its target, as lead already did: a round up to three times its target's speed feels every turn. NASAMS at 1.0 then kills with 92% of its rounds. Gepard crews report downing a Shahed with a brief burst of 7 to 11 rounds; the Paladin took 6.1 bursts, because a burst did 40 damage to a Shahed's 60 and hit a third of the time. A burst now kills with a hit, at hit chance 1.0, and takes about 1.4 a Shahed. For the systems with no published rate, Alex suggested borrowing the rate of a system of the same class, perhaps a point or two lower. Each missile now takes NASAMS's hit chance less 2 points, 0.98, and Merops takes the Sting's less 2, 0.88. Starstreak had been set lower because its darts have no proximity fuze; its three darts each get a chance to strike, which is taken to even that out. In play against Shaheds, Sky Sabre now kills with 91% of its rounds against NASAMS's 92%, the Rapid Ranger 85%, Starstreak 83% and the slower Coyote 73%, and Merops takes 3.3 rounds a Shahed against the Sting's 3.1. The balance laydowns barely moved, and the reference digests did not change. The reference digests were re-recorded: the mixed laydown on seed 7 now ends with no leak and full health, against one leak and 55, and `GAME_VERSION` is 0.13.0.

Alex then asked for three more systems. Sensofusion's Airfence 7 is a Finnish passive RF detector listed at 10 km a sensor over 70 MHz to 6 GHz, at €160,000, and its Military Edition page lists an 800 W portable jammer on eight channels at €40k. Kirintec's K-CEMA NEO is a British manpack jammer and receiver, 45 W over 20 MHz to 6 GHz, and K-CEMA Jupiter is the same family on a vehicle, with almost nothing else published. No jammer here has a published range, and none of the catalogue's jammers had a published power, so there was nothing to scale from. Aaronia lists its 40 W handheld at 2 km; half that, inside the 30 to 60% of claims the fixed site jammer already assumes, is 1 km at 40 W, level with the DroneGun Tactical. Reach going with the square root of power, as the power setting already has it, gives the NEO 1.1 km and the 800 W jammer 4.5 km. A Digitech figure of 1.2 km at 50 W fitted too, but no page carrying it would load, so it was left out. Airfence also finds the pilot and the drone's home point, which the game does not model.

Alex then pointed out that some of these systems are carried, and a carried antenna sits far lower than a mast: say 1.5 m for manpack and 3 m on a vehicle. Every RF sensor and jammer had stood on the same 9 m mast. Each system was sorted by what the real product is: the Wingman, both DroneGuns and the K-CEMA NEO are carried by hand or on the back, while K-CEMA Jupiter, Giraffe 1X, the RapidDestroyer trials truck and the LOCUST are on vehicles, and the 800 W Sensofusion jammer is taken as vehicle-mounted for its power supply. A jammer test showed it plainly: a handheld jammer at 1.5 m can no longer reach a drone 60 m up beyond a 20 m tree line that a 9 m mast clears. The path model does not count ground reflection, which costs a low antenna more again, so this is if anything kind to short masts. The mixed laydown, with two handheld jammers, moved from 14.8 waves to 14.6 over twelve seeds.

Alex then asked whether the fusion node was intelligent enough: whether it knew what to fire at what, how many rounds, and what power to use, and whether it held signatures of enemy drones. It knew less than it should. Effectors took the track nearest the site, jammers came on for any track in reach, fibre-optic drones included, and a model a camera named was only shown, never used. A threat library now gives the fusion node what it may believe about each track, built from the drone catalogue and only from what its sensors have named: a named model's own figures, what a named airframe could be, or anything. A multirotor might be fibre-optic, so the node cannot count on jamming it until it is named.

It was built in pieces and each was measured against the old behaviour, which mattered. Jamming only what a jammer could touch, ranking tracks by the harm they would do over how soon they arrive, and letting RF detectors name a commercial drone's model, as DJI's DroneID allows, each held or helped. Holding rounds while a jammer works was the large gain and the hard part. The first version held fire for any drone whose way in crossed a jammer's reach, judged in an open field, and the mixed laydown fell from about 17 waves to 9 against commercial and Russian drones: its two handheld jammers, 1.5 m up, reach far less through trees than their range, so drones bunched up inside 800 m. Two bugs hid in it too. The check skipped every jammer on the standard trigger, which a catalogue entry leaves unset, and far-out radar tracks came with heights of -100 m or more, so reach to them looked blocked. The hold now judges a jammer's reach over the ground at a believable height, holds only when the way in spends at least 10 s inside it before 800 m, lets go when a jammer has had a drone 10 s and it still flies, and, as a crew would, stops waiting for jammers against a model they keep failing to stop, since drones grow harder to jam each wave. Turning jammer power down to what each target needed was dropped: the power that breaks a control link depends on how far the drone is from its operator, which the node cannot know, and it cost about 1.5 waves.

Over the same seeds as before, one of everything now lasts past 30 waves against commercial drones on four seeds in six, against 24, and 22.3 against the Russian mix, against 19.8, as the jammers save it money. The mixed laydown gained against commercial drones, 19.1 waves against 17.8, held against the generic mix, and lost 1.5 against the Russian mix, 15.4 against 16.9 over twelve seeds, which is near chance and noted for a look.

Next came the drones. Alex asked for the commercial drones commonly used by Russia, and for every drone to fly at a realistic height, speed and agility: a Shahed should fly higher than a Mavic. Research found reported Russian use of the Mavic 3T (a regional government gave fifteen to Russian forces in 2025), the Mavic 3 Pro and the Autel EVO II series (Human Rights Watch in Kherson), with about 300 g of munitions from a leaked Russian manual, and of 10-inch and 13-inch first-person-view drones such as the Veter-10 and Piranha-13. A drone can now fly more than one band, and Shahed-type drones use both. Five lasers gained most, from about 14 waves to about 21, because fixed-wing drones now hold their height above the trees instead of gliding into them, and a laser needs a clear line. The reference digests were re-recorded and `GAME_VERSION` is 0.14.0.

Then the models. Every drone had been drawn as one of two box shapes, a plane or a quadcopter, the same size whatever it was. ## Realism rules

Alex asked whether the sensors, effectors, drones, people and vehicles were as accurate and realistic as possible. The figures mostly were, each with a source or labelled as an assumption, so the gaps were in the rules. Alex chose to fix the rules before the graphics.

A jammer used to bring down every drone it held for 5 s. Now it depends on how the drone is flown. A first-person-view drone flown by hand still comes down, as its flight controller drops it. A DJI or Autel drone, or a reconnaissance drone on an autopilot, turns for home instead, as the Mavic 3 manual describes, and drifts down only if its satellite navigation is jammed too; losing its video only blinds it. A homing module flies a drone through the last 500 m by itself, the figure The Fourth Law and TAF Drones claim, so a new real drone, the last-mile FPV, cannot be jammed close in. Anti-jam antennas had done nothing against GNSS jamming, because jam resistance only reached control and video links; they now cut a Shahed's drift. A reactive jammer cannot follow the Molniya's frequency hopping, which the drone's own source reports.

Missiles now have a minimum range: Starstreak's published 300 m, CAMM's reported "under 1 km" taken as 1 km, and the same by class for the rest. Crews had seen drones only 100 to 200 m off. Two field trials found half of their observers saw a small quadcopter at 245 to 307 m, both where its span filled 0.065°, so the rule is now that angle: about 290 m for a 7-inch quad and 2.2 km for a Shahed. Crews also hear loud drones, so a soldier with a jammer can turn to a Shahed at night by ear. Plain machine guns and the Gepard now lose three quarters of their hit chance at full range, as their spread grows, where airburst guns lose a quarter; the Gepard's figure was raised so that at about 3 km it still matches crew reports. Armour halves a strike on the Gepard, the Skyranger, the Stormer and anything on a Patria. An acoustic sensor's bearing points to where the drone was when the sound left it.

Balance, measured with `npm run balance` on three seeds, did not move where the new rules apply: the jammer, interceptor and mixed laydowns lose in the same waves as before, and the five reference runs end with the same kills, leaks and budget. The laser laydowns moved by up to three waves either way (three lasers and a radar: waves 17, 14 and 16 became 19, 17 and 15). That came from the new last-mile FPV alone, not a rule: the fusion node judges an unnamed track by the average of every drone it knows, so one more quadcopter in the catalogue changes how it ranks threats. With that drone taken out, the laser laydown loses at 17, 14 and 16 again.

The game version went to 0.17.0, as old saved runs no longer replay the same, and the reference digests were recorded again.

Alex then asked whether the jammers and the fusion engine were smart enough. The tracking is realistic: a Kalman filter per track, statistical gating, triangulation from bearings with the ghosts that brings, and SAPIENT messages with their delays. The decisions had gaps. The fusion node ranked a drone flying away as urgent as one flying in, because it divided distance by speed, and it held fire for a reactive jammer that the last change had made unable to follow a Molniya. The second was a one-line fix. Ranking by closing speed instead turned out worse: four of six mixed runs let strikes through where none had, because a track's velocity from bearing-only sensors can point anywhere and emitter-seeking drones fly at a radar further out, not at the site. So ranking stays by speed, and closing speed is used only to leave alone a drone that is flying away from the site and heading for none of your systems. In the first mixed wave the only track it now leaves alone is a ghost, made where radar and RF bearings crossed, drifting away: an interceptor had gone after it, so now the interceptors take all five drones before the jammers are needed. In the reference runs the mixed runs killed one more and two fewer drones, and the second let none through where one had. Over three seeds the mixed laydown lasted 19, 12 and 17 waves, against 15, 14 and 14; the laser laydowns moved by a wave or two either way, about their spread from one change to the next.

Alex then asked for the other gaps to be fixed. An unnamed track is now judged by the drones the waves send, as intelligence on the enemy would say, so adding a drone to the catalogue no longer moves play. A launcher is offered a track only if its round can meet it within reach, worked out from where the track will be, so a slow interceptor drone is not sent after a faster drone flying past. Threat distance is measured to a drawn area's outline. The AUDS, on a pan-and-tilt head, is turned onto the drone when it has a sector antenna. Video links are now jammed where the pilot receives them, at the launch point, so a jammer by the site rarely reaches them, and the fusion node counts only on breaking a control link. Two techniques were added: GNSS spoofing, which turns a navigating drone steadily off course, as Ukraine's Pokrova is reported to, and taking over a commercial drone, which lands it whole, as D-Fend's EnforceAir claims. Last, free effectors are paired with threats, most urgent first, each threat going to the cheapest effector per kill with a fair chance at it, and a threat already engaged is left to that engagement until it comes close. A first try let a missile join a quadcopter a laser was already burning, because a beam is not counted as rounds in the air, so the engaged check came in.

Together these changed play little, and mostly for the better: over three seeds the mixed laydown lasted 13, 18 and 15 waves against 19, 12 and 17 before, the laser laydowns about the same, and five lasers with all-round radars 29, 29 and over 30 against 26, 29 and 26. ## Checking SAPIENT against the standard

Alex asked whether the SAPIENT emulation really follows BSI Flex 335. A two-wave run was recorded without a browser and every message parsed strictly against Dstl's official v2.0 `.proto` files, with the standard's own required-field and ID rules. All 10,040 parsed, but every registration broke a rule: modes without a settle time or task definition, class definitions without levels, and no node declaring the commands it accepts. A real fusion node could not have known a camera can be pointed or an effector told to engage. Registrations now declare `look_at`, `mode_change` and the `Engage` request where they apply, the RF directed-energy weapon is `NODE_TYPE_RFDEW` rather than a laser, fused tracks flying away say Departing, and the in-game validator checks registrations as the standard does. The same run now gives 10,039 conformant messages, the other being the deliberate injected fault. Every reference run kept its waves, kills, leaks, health and budget, but four digests were recorded again: they hash the text of the newest messages, and fused reports now saying Departing changes that text. `docs/SAPIENT.md`, linked from the README since the handbook began but never written, now records the message flow, the deliberate departures from the standard and what a live link to real equipment would need.

## Sight lines for guns and beam-riders, 9 November 2026

## Radio reach by band, and finer paths, 9 November 2026

Alex then asked for the audit's two small radio gaps to be fixed. An RF detector's open-field reach took no account of frequency: a 900 MHz link was heard no further than a 5.8 GHz one of the same power. It now goes with wavelength, as the Friis equation gives for the same antenna gain on every band, against the link each detector's range is quoted for: a small first-person-view drone's 2.4 GHz control link. A video sender is taken to be 5 dB louder than a control link, the figures in the config's own link budgets. Every detector keeps its quoted range against the first-person-view drone. A wide detector now hears the spotter's 900 MHz link at 15.1 km, not 5.5 km, and one that covers only 2.4 and 5.8 GHz hears its video at 2.4 km, not 3.2 km. A detector deafened on 2.4 GHz by one of your own jammers hears a first-person-view drone's video at three quarters of the range.

A radio path was sampled at 64 points, so beyond 1.3 km a point stood for more than one 20 m cell, and at 14 km for eleven. It now has up to 256 points, one for every cell out to 5.1 km. Reading every cell on longer paths, and taking the highest cell in each step, were both measured and not done: every cell gave the same mean predicted ranges to three figures, and a range prediction for the large RF detector then took 39 to 56 ms against 27 to 30 ms. The finer profile matters more in play than in the mean. The medium radar used to track the first drone of a wave 5.8 km out, partly through ground its samples had stepped over, and now first tracks it at 3.2 km, 86 s later. The reference runs take about 12% longer.

The five reference digests were recorded again. Over 16 seeds of the mixed laydown the means moved little: kills from 64.9 to 66.2 and strikes on the site from 2.3 to 1.7, the gain coming from the frequency term. Two tests that waited 300 s for a first engagement request now wait 450 s. Four new tests fail on the old behaviour and pass on the new, and the full frontend suite passed 1,980 of 1,980. `GAME_VERSION` is 0.19.3, as saved runs no longer replay the same. A browser check on a throwaway account and database, removed afterwards, showed the detector cards with the new reach against a large drone. The measured tables in `FUSION_AND_TARGETING.md` predated the change, and the script that made them had not been kept. No commit or push was made.

## Measuring the picture again, 10 November 2026

Alex asked for those tables to be measured again. The script was written afresh from the page's own definitions, as `frontend/tools/measure-fusion.js`, run with `npm run measure`. It plays each run as the reference test does, looks after every step without changing anything, and stops if a reference run does not end on its recorded digest. To check it, it was first run with the two radio changes switched off. It gave every figure in the old tables but one, a median that came out at 8.1 s where the page said 8.4 s. Getting there settled three things the page had not said: errors are sampled on the whole second, a percentile is the nearest value and not one worked out between two, and a track counts as linked to a drone only once it is confirmed.

The new figures show what the radio changes did to the picture. The mixed runs confirm fewer tracks (867, was 951) and fewer ghosts (199, was 235). Spotters are now heard on their 900 MHz link at a median 13.2 km, so 77% are first detected by a bearing-only sensor (was 45%), and they wait longer for a confirmed track: 116 s in the median, and 237 s at the 90th percentile where it was 133 s. Tasking wastes a little more: 36% of Engage tasks in the mixed runs went to a track with a real drone at it, where it was 40%. The page now says how the figures moved, and that the same eight runs are compared, so some of each difference is one seed's luck.

The check had a cost. It switched `propagation.js`, `rf-model.js` and the reference digests back in the shared working tree, a minute at a time, and another session committed the tree in one of those minutes. Commit dece516 therefore carries 64 points a path and no band term under a message saying the reverse, and its own new tests fail there. The commit after it puts both back with their digests. ## Finding your way round the map, 9 November 2026

Alex asked for easier ways to get round the map. The camera already followed the mouse, touch, the minimap and a few fly-to buttons, but took no keys, gave no sense of north once turned, and could not frame what had been built. ## A whole-code audit and its fixes, 10 November 2026

Alex asked for the whole codebase to be examined for bugs, poor quality and waste, and then for every finding to be fixed. Eight reviewers read a clean copy of `main` by area, one of them for security, and each finding was checked again in the code or by running it before it was reported. Twenty were reported. The tests, the build and the lint passes were clean, so most of what was found was in the game's rules.

The three that mattered most were these. A round was counted as having hit the ground when it was less than 4 m above it, and a machine gun's muzzle is 2.6 m up, so about half the heavy machine gun's rounds at low drones were removed in their first step. The fusion node listed its live tracks before it put a killed drone's track on kill watch, so the effector that had just made the kill was sent straight back to it and lost a second. And a patrol's escort was checked against catalogue prices but charged at its price on the vehicle's mast, so a patrol could be dropped at the first wave, or take the budget below zero and leave the escort without a link.

The rest were smaller: an effector switching target could join a track another already held, a refused task still counted as a pairing, jammers were stood down whenever a track missed a scan, a deployed pack taken away during a run left nothing able to fire, Remove on a patrol vehicle sold the system beside it, the coverage score worked out four whole-world grids to score a small area (2.4 s after every change), the coverage cache ignored jamming, unticking auto-start during the countdown did nothing, a new recovery code could be lost before it was noted, real hills were painted as snow, the placement preview used the wrong price, and three texts said what the game does not do. In the map builder a fit error that was not a number passed the 5 m check, a dropped download was not tried again, and the count checks and the satellite step could throw away the lidar after it had been fetched. On the backend a pack header holding an infinite number broke the pack list, the scrypt cost went up to one of the settings OWASP lists (N 2^14, p 5; older hashes still verify), and the builder now refuses a redirect that leaves https.

The three tasking changes move every run, so the five reference digests were recorded again and `GAME_VERSION` is 0.20.0. Over 16 seeds of the mixed laydown the means went from 66.2 kills, 1.69 leaks and a site at 50% to 68.9, 1.25 and 62%; single seeds moved both ways, as they always have. The jammer change alone measured no better than before (65.3 kills), and the other two together gave nearly all the gain, so it is kept for the behaviour, not the score. The tables in `FUSION_AND_TARGETING.md` were measured again. Each fix has a test that fails on the old code. About thirty smaller points from the audit were not reported or fixed; they are listed in the plan.

Alex then asked how the game could be made quicker and smoother for players, and for as many of the answers as could be done without breaking anything. The second pass kept to changes that tests could prove and that leave the reference runs as recorded: time stamps built once a step, the Plan tab's coverage worked out a few rows a frame, a guard round the frame loop so a fault pauses the game and says so, the dock's canvases and the 3D view following the display's scale, toasts read out by screen readers, a warning before a page showing a recovery code is left, and a dozen smaller slips in numbers and messages. Three things were left because they cannot be judged without watching the screen or need a decision: London's frame rate, the four-second pause while generated ground is made, and the arrow keys entering replay.

## Playing it as a stranger, 11 November 2026

Alex asked what makes the game awkward to use and hard to follow: the workflow, the SAPIENT side, and how it is used. The audit the day before had read the code. This time the game was played by hand as a new player, from making an account to the results card, while two readers went through the journey and the SAPIENT panel in the code. Each claim was then checked on the screen or in the code before it was reported, and two things that looked like faults turned out to be the test's own doing and were left out.

The run that settled the ranking was a small one. Wave 1 sent five first-person-view drones. The Run box ended it at 1 kill and 0 leaks, and a toast said "Wave 1 cleared". Four of the five had come down on the radar, which was destroyed. The fusion node had raised three critical alerts as it happened, to the "C2 Operator GUI", which is the player, and the game had accepted each one on the player's behalf without showing it. The Statistics tab and the Messages tab had the truth, the second under a list that was two thirds heartbeat. Thirteen points were reported, in order.

Alex asked for the first five to be fixed. The Run box now shows site integrity and the budget left through a whole run, which reverses an earlier choice to keep them for the sandbox, and counts drones that hit your own systems. The fusion node's warnings show above the timeline. The Messages tab opens on tasks, answers and alerts, with status reports and raw detections a click away, and its filters work on a frozen list. Start wave carries its lock warning on the button, and the wiring warning stays until it is answered. Space pauses after a click.

Checking on screen changed three of the five. The lock note was first a line under the button, and at Alex's window height it pushed the Controls box into scrolling, so it moved onto the button. The PAUSED note was first a line above the timeline, where the SAPIENT panel covered it, so it moved into the timeline's row. And the first fix for Space did not work at all: it asked the browser whether the button had been focused by keyboard, and a browser answers yes for a clicked button as soon as any key goes down. The tests had passed because they stood in for that answer. The hook now remembers the button the pointer last pressed, and the test presses it.
